# Reflection: walleye coordinator (local_7fb92f70), for the structure review, 2026-11-23

Written from what I see in the folders now (git worktree list, ls, device.toml, build-kernel.sh header). What I did not look up is marked "not known".

## 1. Role in two lines
Lane coordinator for the Pixel 2 (walleye): I order the lane's backlog (google-walleye-lab `data/backlog.json`), start one keeper, builder and researcher at a time (max 3 sessions), record the author's words and the go items, and land the records. I never touch the phone or build anything; keepers hold the lease and run procedures, builders write them.

## 2. The flows as they really run (repo: google-walleye-lab unless said)
- **Research**: a research session (worktree `~/Projects/linux-phone-oco/wt-walleye-research-<ts>` or `~/.local/share/agent-worktrees/google-walleye-lab/...`) writes an `ikb research` row (`data/` tables, generated `docs/*.md`), branch `walleye-research/...`, `land`. Outside reads: kernel.org, lore, Android kernel (not in a repo of ours).
- **Decision**: I (or the lane) write `ikb decision` in the same repo, citing the research ids. The author's words go to marshall-oco/conversation through the Top; I copy them verbatim into the backlog item's note (so the words live in two places).
- **Build**: a builder in `wt-walleye-builder-<ts>` or `~/.local/share/agent-worktrees/google-walleye-lab/walleye-builder/<item>`, branch `walleye-builder/<item>`. It edits `procedures/*.rs`, `tools/*`, `build/*.sh`, `dt/*.dts`, `rootfs/`, `device.toml` (`[images.X]` sha256 is the declared image). Kernel and images are built in `~/Projects/walleye-build/` (outside any repo, 84 GB, 176 entries); a fresh worktree needs `ln -s ~/Projects/walleye-build build/images`.
- **Phone try**: a keeper in `wt-walleye-keeper-<ts>`, branch `keeper/<item>`, takes the lease (`lpoco-lab keeper`), runs `procedures/<name>-on-the-pixel-2.rs` with lpoco 0.41. The go is `ikb backlog-go --id <item> --until <date>` on an item with `--witness person`; the procedure runs only when the go row names the image sha256. The run's raw log lands at the top of `~/Projects/linux-phone-oco/` (`rootfs-boots-run-2.out`, `.log`, `pmic-run4.log`), not in a repo.
- **Record**: the keeper writes research and a session log on `keeper/<item>` and lands; when `land` conflicts I close the PR and replay with `ikb` on a fresh branch from main (six times on 2026-11-22: scripts are in my scratchpad `.../scratchpad/run1-replay.sh` etc., not kept anywhere durable).
- **Upstream**: items `walleye-upstream-board-dts-next` and `walleye-upstream-panel-series`, docs under docs `upstream/` and `~/Projects/linux-phone-oco/upstream-queue`, `docs-upstreams` (not known which of the two is the live one). Nothing went upstream; the author's go is needed.

## 5. What would have stopped the incidents
- **Land/regen conflicts** (two PRs within minutes conflict on `data/*.json` and `docs/*.md`): (a) the generated files are not committed in PRs but regenerated on main by one job after merge, or (b) `land` serialises per repo (one landing at a time with rebase-then-regenerate), or (c) each record is its own file (append-only, one file per row) and the tables are only the generated view. I replay by hand today.
- **A go window erased by a note**: re-entering an item (`ikb backlog` with a new note) clears go, witness, blocked_by and waits. A go should be its own record (item, sha256, until) that an item update cannot clear, or `ikb backlog` should refuse a change that drops an open go unless `--clear-go` is given.
- **A look skipped as "waits on author"**: `--waits` is free text, so the keeper read it as "do not run". The author had said the go was open. `lane-next` lists dropped items first and prefers in-progress items to ranks, so a keeper took another item. A keeper run should be started for one named item, and "waits" should be a link (`--blocked-by` an open go or decision record) that the go record clears itself.
- **My own errors**: I told the Top "done" when a builder had only started. Notes to the Top should be read off `tad q`, not written from memory (practice 25 and 29).
